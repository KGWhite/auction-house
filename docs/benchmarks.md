# 基準測試（Milestone 1 第一組數字）

目的：建立一個可重現的基準，之後的里程碑（快取、佇列、WebSocket…）才有東西可以比較。
本階段**沒有**效能目標；重點是確認在 50 個並發玩家爭搶同一場拍賣時，系統仍然正確（結束後 `reconcile` 全部成立）。

## 測試方式

`make k6-smoke`（`k6/run-smoke.sh`）：

1. `cmd/k6prep` 建立臨時資料庫，套用遷移，建立 50 位同區間玩家（各 1 兆金幣）與 1 場拍賣（起標價 1000）。
2. 啟動另一個 server 容器（`ah-smoke-server`）連到該資料庫。
3. k6：50 個虛擬使用者（每人一位玩家）對**同一場拍賣**持續出價 30 秒，
   每次請求都帶新的 `Idempotency-Key`，金額取自上一個回應的 `min_next_bid`
   （成功回應或 409 `bid_too_low` 都帶有新的最低價；「已是最高者」時重新讀取拍賣）。
4. 結束後對該資料庫執行 `reconcile`，然後刪除臨時資料庫。

這是**最壞情況**的爭用：所有請求都集中在同一列 `auctions` 上，被 `SELECT … FOR UPDATE` 序列化。
沒有思考時間（think time），所以量到的是系統在飽和時的行為，不是一般玩家的流量。

## 目前的基準：全部在 Docker 內（2026-10-16 更新）

專案改為完全 Docker 化後重跑。k6（`grafana/k6`）、server（alpine 映像）、PostgreSQL 16（`postgres:16` 容器，預設 `fsync=on`，`max_connections=300`）
都是容器，透過 Docker 網路連線；執行方式是 `make k6-smoke`。硬體同下表（Docker Desktop 的 WSL2 後端，同一台機器）。

| 回合 | 設定 | 請求數 | 吞吐量 | 成功出價 | p50 | p95 | p99 | max |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **D（目前基準）** | 線性增額（0% + 10） | 30,987 | **1,031 req/s** | 733（24.4/s） | 48.6 ms | 66.7 ms | 86.1 ms | 157.5 ms |
| E | 預設規則（5% + 10） | 24,300 | 808 req/s | 425（14.1/s） | 43.7 ms | 65.1 ms | 83.9 ms | 97.4 ms |

狀態碼（出價請求）：D 為 200 2.4% / 409 97.6%；E 為 200 1.7% / 409 73.3% / 422 25.0%。兩回合結束後 `reconcile` 都顯示所有不變量成立。

比下方原生數字低約 15%：多了一層容器網路與 Docker Desktop 的虛擬化，PostgreSQL 的資料也在容器的儲存層。結論不變：
瓶頸是同一場拍賣的列鎖。之後請拿 D 回合當比較基準。

## 結果

三回合，每回合 50 VU × 30 秒，完整原始輸出見 `k6/out/`（已加入 .gitignore，由腳本產生）。

| 回合 | 設定 | 請求數 | 吞吐量 | 成功出價 | p50 | p95 | p99 | max |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **A（基準）** | `fsync=on`，線性增額（0% + 10） | 36,517 | **1,216 req/s** | 869（28.9/s） | 42.1 ms | 51.1 ms | 56.7 ms | 162.5 ms |
| B | `fsync=off`，線性增額 | 36,994 | 1,232 req/s | 876（29.2/s） | 41.2 ms | 52.7 ms | 59.2 ms | 86.2 ms |
| C | `fsync=on`，**預設規則**（5% + 10） | 26,396 | 878 req/s | 425（14.1/s） | 35.2 ms | 52.2 ms | 58.0 ms | 81.9 ms |

## 如何解讀

- **幾乎都是 409，是這個情境的本質，不是錯誤**。50 個玩家同時用「我知道的最低價」出價，
  同一個價格只有一個人能贏，其餘都拿到 `bid_too_low`（附新的最低價）後重試。
  `already_top_bidder` 與 `bid_too_low` 同為 409。
- **成功出價只有約 29/s，但總請求量約 1,200/s**：被拒絕的請求仍要取得拍賣列鎖、讀取、再回滾，
  成功的出價則要在持鎖期間做約 15 個語句（鎖兩位玩家、寫 bid、凍結、解凍、兩筆帳本、更新價格）。
  瓶頸是同一把列鎖，不是 CPU：這正是下個階段「在鎖之前先用快取／記憶體擋掉明顯過低的出價」可以改善的地方。
- **`fsync` 幾乎沒差（A vs B）**：在這台機器上，限制吞吐的是鎖與往返次數，而不是 WAL 刷盤。
  A 回合的 max 162 ms 是單次尖峰。
- **回合 C（預設的 5% 增額）**：價格呈指數成長，約數百筆成功出價後就超過玩家餘額，
  之後約 30% 的請求變成 `insufficient_gold`（422）。這就是為什麼基準回合 A 使用線性增額，
  才能在 30 秒內持續測到「成功出價」的完整路徑。`k6/run-smoke.sh` 可用
  `SMOKE_INCREMENT_PERCENT` / `SMOKE_INCREMENT_MIN` 覆寫。
- p99 與 p50 只差約 15 ms：延遲主要是排隊時間（50 個並發 ÷ 約 1,200 req/s ≈ 41 ms），分佈很集中，沒有長尾。

## 重現

```bash
make k6-smoke           # 需要 k6；DATABASE_URL 指向的伺服器上要有建立資料庫的權限
SMOKE_INCREMENT_PERCENT=5 make k6-smoke   # 回合 C
KEEP_DB=1 make k6-smoke                   # 保留臨時資料庫以便檢查
```
